## How it deploys

GitHub Pages serves the `main` branch as-is. There is **no build step**, no
bundler and no framework — static HTML, CSS and vanilla JavaScript, committed
in the shape they are served in.

`.nojekyll` at the repository root stops Jekyll from processing the tree, so
directories beginning with an underscore and files Jekyll would otherwise
rewrite are served exactly as committed. **Do not delete it.**

There is **no `CNAME` file**, and there should not be one unless a custom
domain is deliberately set up. On a `github.io` user site a stray CNAME
silently redirects the whole site elsewhere. The validator fails if one
appears.

`.github/workflows/validate-site.yml` runs the validator on every push and pull
request. It does **not** deploy — publishing stays a plain Pages operation.

### The shared shell

`assets/js/shell.js` injects the header and footer into every page, so
navigation cannot drift between wings. It resolves the site's base URL from its
own `<script>` URL, which is why pages work from any directory depth without
knowing how deep they are.

Pages use **relative** paths for CSS, JS and the favicon (`../../assets/...`).
`404.html` is the one exception: a 404 is served under whatever path the visitor
asked for, so it has no fixed depth and uses **root-absolute** paths instead.

If JavaScript fails, every page's content is still readable — only the chrome is
missing, and each page carries a plain-HTML fallback link home.

## The registry

`data/projects.js` is the single source of truth. It is an **allowlist**:
nothing appears anywhere on this site unless it has a record there, and no page
queries the GitHub API at runtime. If a repository is renamed, made private or
deleted, the site keeps working and simply shows what this file says.

Everything downstream reads from it — the wing pages, the homepage, the card
counts in every wing header, the star map, and the sitemap.

> **This file is public.** It is served at `/data/projects.js` and anyone can
> read it. Do not put private repository names, credentials, client-sensitive
> data, secrets or confidential metadata in it. `unlisted` controls *rendering*,
> not access. If something must not be read, it must not be in the file.

## Statuses and visibility

These are **two separate fields** answering two different questions. They used
to be one, which is why a record could be "hidden" as though that were a kind of
work.

`portfolioStatus` — **what the work is.** Public; a visitor sees it as a badge.

| value | meaning |
|---|---|
| `showcase` | complete enough to represent professionally |
| `prototype` | functional or meaningful, still evolving |
| `research` | exploration is the point; the outcome is a finding |
| `workshop` | small, worth showing, not a major piece |

`visibility` — **whether it renders.** Internal; never shown to a visitor.

| value | meaning |
|---|---|
| `public` | appears in its wing, the counts, the map and the sitemap |
| `unlisted` | never rendered anywhere; the record is kept so the decision and its reason survive |

The filter is **fail-closed**: `cards.js` renders a project only if
`visibility === "public"` exactly. A missing or misspelled value means the
project does not appear — an absent project rather than an accidentally
published one. The validator catches the typo.

Do not use `private` as a value. It would be untrue in a public file.

## Category worlds

Each wing is allowed to look like itself. `assets/css/worlds.css` re-points
three custom properties per world, keyed off `data-world` on `<html>`:

```html
<html lang="en" data-world="research">
```

A world re-points variables; it does not introduce new colour. Adding a world
means adding a block there and a record in `CATEGORIES`.

**Games is a first-class discipline and does not merge into Software.** The wing
is intentionally sparse — the current entry is a design document, not a released
game — and its copy says so plainly rather than padding the shelf.

## How to add a project

1. Append a record to `PROJECTS` in `data/projects.js`. Required: `id`,
   `title`, `category`, `portfolioStatus`, `visibility`, `summary`.
2. Write the summary to **scan**: what it is, what question it addresses, why it
   matters. Detail belongs on the case study, the methods page or the repository.
3. Add only links that exist. A `null` link is never drawn, so there are no dead
   buttons.
4. **Add no metric that is not traceable** to a notebook, README or other
   document. Where a figure could not be verified, say so in `metricsNote` — the
   registry already does this in several places and it is the most valuable habit
   in the file.
5. Regenerate the files that mirror the registry:
   ```sh
   node tools/sync-static.js
   ```
6. Validate:
   ```sh
   node tools/validate-site.js
   ```

Counts in wing headers update themselves — see [Generated files](#generated-files).

## How to add a Selected Work entry

Edit the `SELECTED` array in `data/projects.js`. It is a list of ids, in display
order, and it is a **curatorial decision, not a sort** — nothing is chosen
automatically.

The reasoning behind the current set is written in a comment directly above the
array, including what is deliberately absent and why. **Update that comment when
you change the list.** A curated set whose rationale is undocumented becomes an
arbitrary set within a year.

Rules of thumb kept so far: six to nine entries; strong research is never dropped
to even out the category histogram; and Games does not enter until something is
playable.

## How to add a case study

1. Create `<<wing>>/<<project-id>>/index.html`. Copy an existing case study —
   `software/key-to-stl/index.html` is the fullest — and keep the `<head>` block
   intact, updating `title`, `description`, `canonical` and the `og:`/`twitter:`
   tags. Canonical and `og:url` must match the page's real URL; the validator
   checks this.
2. Set `data-world` on `<html>` to the wing's category id.
3. Point the registry record at it: `caseStudy: "/software/key-to-stl/"`.
4. Run `node tools/sync-static.js` — the star map's list and the sitemap pick it
   up automatically.

## Generated files

Two things repeat what the registry already knows, so they are generated rather
than typed:

| file | what |
|---|---|
| `map/index.html` | the star map's list view, between the `CC:MAP-INDEX` markers |
| `sitemap.xml` | one entry per public page, including case studies |

```sh
node tools/sync-static.js           # write them
node tools/sync-static.js --check   # report drift, change nothing
```

The map's list is **static HTML on purpose**. It is what a visitor without
JavaScript, a screen reader and a narrow phone actually get; the figure above it
is a second view of the same content. If that list were built by script, the
sentence next to it would be false.

Wing header counts work differently and need no regeneration. The markup carries
a placeholder with the last-known text inside it:

```html
<span data-cc-count="design" data-cc-noun="project"><b>3</b> projects</span>
<span data-cc-breakdown="design">3 showcase</span>
```

`cards.js` replaces the contents on load with the live figure. The static text
inside is a real fallback — it is what a reader without JavaScript sees — so the
validator checks that it is *also* true.

## How to run validation

```sh
node tools/validate-site.js
```

No dependencies; Node's standard library only. Exit code 0 passes, 1 fails, and
every failure prints what is wrong and where. It checks:

- **registry** — ids present and unique, categories/statuses/visibility valid,
  no `private`, nothing unlisted in a visible collection
- **selected work** — every id exists and is public, no duplicates
- **paths** — case studies, images, local live links and category paths all
  resolve on disk
- **metadata** — title, description, canonical, `og:title`/`description`/`url`/
  `image` on every page; canonical matches the page's own path; `og:url` matches
  canonical; `og:image` exists; `twitter:card` implies `twitter:image`; 404 is
  `noindex`
- **images** — every `<img>` has `alt`; every local image exists
- **legacy** — fails on `candicecantrelle.com`, on `/candicecantrelle.github.io/`,
  on a `CNAME` file, and on `/archive/` returning to production
- **counts** — every wing stamp uses a placeholder, and its static fallback
  matches the registry
- **generated** — `sync-static.js --check`, plus sitemap entries resolving on
  disk and excluding the archive and the 404

Run it before every commit. CI runs it too, but a red CI badge is a worse place
to learn than a terminal.

## The share card

`assets/og-card.png` (1200 × 630) is referenced by `og:image` and
`twitter:image` on every page. Its source is `tools/og-card.html`, which is a
real page using the site's own `tokens.css` — change a colour in the design
system and the card changes with it.

To regenerate:

```sh
npx playwright screenshot --viewport-size=1200,630 tools/og-card.html assets/og-card.png
```

Or open it in a browser at 1200 × 630 and screenshot it. The card is set in
IBM Plex Mono, which is the site's chrome face, so it reads as this portfolio
rather than as a generic social banner.

## Why `/simulation/` differs from `/simulations/`

The Simulations **wing** is at `/simulation/`. The standalone **atlas** is at
`/simulations/`, published from
[`Unicorn0-0Cakes/simulations`](https://github.com/Unicorn0-0Cakes/simulations).

They differ by one letter for a real reason. GitHub Pages serves a project site
at `/<repo>/` **in preference to** a same-named directory in the user site, so
while the atlas repository publishes at `/simulations/`, this repository cannot
use that path — anything committed there would be unreachable. The wing
therefore uses the singular, which is also the discipline name on the homepage,
and links out to the atlas.

`data/projects.js` encodes this as an explicit `path` on the Simulations
category. Every other category derives its URL from its `id`; only this one
overrides it. `cards.js` `catPath()` is the single place that reads it.

If the atlas ever stops publishing to `/simulations/`, this can be reverted —
but there is no reason to.

## Preserving old versions without publishing them

The previous portfolio was removed from production in August 2026. It carried
marketing copy, testimonials and engagement figures that could not be
substantiated, and publishing unsupported claims for the sake of transparency is
not transparency.

**Nothing was deleted.** The site as it stood, including the whole `/archive/`
wing and its 45MB of images, is preserved at the tag:

```sh
git checkout legacy-site-archive          # inspect the old site
git show legacy-site-archive:archive/index.html
git checkout main                         # come back
```

Use the same pattern for anything else being retired: **tag it, then remove it
from `main`.** Git history is sufficient preservation, and it keeps large dead
assets out of what visitors download. The validator fails if `/archive/` returns
to production or if any page links to it.

Do not rewrite history, and do not delete the source repository
`Unicorn0-0Cakes/candicecantrelle.github.io` — it remains the backup of the
pre-migration site.

## Local preview

Serve from the repository root, because this is a user site mounted at `/`:

```sh
python3 -m http.server 8000
```

Then open http://localhost:8000/.

Opening the HTML files directly with `file://` will not work — the shared shell
resolves its base from the script URL and the registry is loaded over HTTP.
