TerritoryOne

A routing prototype built on one rule that costs it money: a homeowner request belongs to exactly one contractor, decided before anyone is contacted, and never sold twice.

If a lead can be sold to five contractors, what exactly did any of them buy?

01What it is

TerritoryOne is a working demonstration of a lead-routing system for independent home-service contractors, scoped to residential air-conditioning repair and replacement and to small companies — roughly two to fifteen employees. A homeowner submits a request; the system validates it, resolves it to a ZIP-based territory, and delivers it to the single contractor who holds that territory. There is no bidding, no auction, and no resale.

Calling it a lead-generation site undersells the design problem. The generation part is a form. The system is the part that decides whether a submission is real and who it now belongs to.

02The problem

The shared-lead marketplace model sells the same homeowner to several contractors at once. For the marketplace this is efficient; for a two-truck HVAC company it means paying for the right to be fourth to call, and for the homeowner it means five phone calls in an hour. The product everyone is nominally buying — a customer — is not what changes hands. What changes hands is a contact record with an unknown number of copies.

So the design question is not how to collect more requests. It is what would have to be true structurally for a request to be worth something specific to one business.

03The system

Routing is resolved at capture time rather than reconciled afterwards. Each contractor gets a single-tenant landing page for their own service area, so the territory is already implied by where the homeowner arrived; the ZIP field then confirms it.

  1. 01Territory landing pageOne page per territory, belonging to one contractor. The routing decision starts before the form is opened.
  2. 02Homeowner intakeName, service address, contact phone, service type — repair or replacement — urgency, and the service ZIP.
  3. 03ValidationService-area coverage, service type and contact details are checked before the request is treated as a lead.
  4. 04Duplicate checkRecent submissions are checked so the same job is not routed twice. A lead’s value depends on it being singular.
  5. 05Territory resolutionThe ZIP resolves to exactly one territory. Anything outside covered ZIPs is set aside for manual review rather than dropped or force-fitted.
  6. 06AssignmentThe request becomes the property of the one contractor who owns that territory. There is no second recipient.
  7. 07Contractor actionThe contractor works the request from a dashboard — status changes, notes, follow-up — against a record with a submission timestamp and a visible trail.

Fig. 1 — intake to ownership. Steps 03–05 all run before anyone is contacted.

04The territory model

Exclusivity here is an inventory constraint, not a marketing promise. If a ZIP range maps to one contractor, then the number of contractors the product can sell to is fixed by geography, and revenue per territory is capped by construction. That is an uncomfortable property for a lead business, and it is the whole idea: a scarce thing can be priced; an unlimited thing has to be sold on volume.

Two further constraints follow from the same commitment. Qualification happens before handoff, because a promise of exclusivity is worthless if the exclusive thing turns out to be a duplicate or an out-of-area request. And pricing is kept off the platform entirely — the site says so plainly, describing it as a conversation rather than a checkout. While the territory model is unproven, self-serve pricing would be committing to numbers the product has not earned the right to quote.

The homeowner side carries its own boundaries: submissions are used only to respond to that service request — no newsletters, no remarketing, no third-party list resale — and records carry a stated ninety-day retention, a submission timestamp, and a trail the receiving contractor can see. In a category that resells contact data by default, a declared retention limit is a product decision.

05A different system from Bayou Vendor Records

Both are small operational prototypes in this wing, and they are deliberately not the same shape.

TerritoryOne

Validation → allocation → routing → ownership. The interesting moment is a single decision made once, correctly, before anyone acts.

Bayou Vendor Records

Record → status → expiration → attention. The interesting moment is a state accumulating quietly until it needs a person.

06My role

Product concept, the system rules — exclusivity, qualification before handoff, duplicate suppression, out-of-area handling — the territory model, the intake and routing workflow, the two-sided interface direction, the homeowner data boundaries, the commercial model including the decision to keep pricing off-platform, and deployment of the working demo.

The application was built and directed on an agentic development platform — Polsia — rather than from a blank repository. The rules the system enforces, and the reasons it enforces them, are the work I am showing here.

07Current status and limitations

This is a demonstration. The contractor in it does not exist.

The live site runs in demo mode on synthetic data, and says so: the example company is fictional and used only to demonstrate the intake and validation path. There is no live service behind it.

No paying contractors, live traffic, lead volume, conversion rate or customer traction is claimed anywhere on this page, because none of it exists to claim. What has been built is the routing model and a working homeowner-facing path through it.

Also:

  • The contractor dashboard is behind sign-in and was not publicly inspectable, so it is described here only as far as the product surface documents it.
  • Territory coverage in the demo is ten ZIP codes. Whether ZIP-range exclusivity holds up against real service-area geography — which does not respect postal boundaries — is the first thing a pilot would have to test.
  • No public repository exists for this project, so no source link is offered. The implementation stack is not enumerated here; see the technology note in the sidebar.
