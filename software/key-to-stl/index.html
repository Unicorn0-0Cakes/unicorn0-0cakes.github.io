Key → STL

One idea — recover a printable profile from an ordinary photograph — delivered four different ways, because the delivery turned out to be the hard part.

Prototype
Python · FastAPI · OpenCV
2026

How much of a physical object can be recovered from a single ordinary photograph?

01What it is

Key → STL takes a photograph of a physical key and produces an STL file you can send to a 3D printer. It exists as four separate delivery surfaces built over one idea: a processing core, an HTTP service that wraps it, a browser client, and a standalone desktop application for people who will not upload a photograph of their key to somebody else's server.

02Why

The interesting question is not whether you can 3D-print a key — you can — but how much geometry survives the trip from a three-dimensional object, through a lens, into a flat array of pixels, and back out into a solid. A key is a good test case because it is almost two-dimensional, its important features are small, and you can tell immediately whether the result is right: it either turns or it does not.

03My role

All of it. The OpenCV work, the FastAPI service and its licence integration, the browser client, the desktop application and its build scripts, the GitHub Actions workflow that produces executables, and the documentation — including the photography guidelines, which turned out to matter more than any single algorithmic choice.

04How it works

Capture
Documented requirements: vertical orientation, plain light background, even diffused lighting, no glare on the metal, sharp bitting edges, at least 1920×1080. Almost every failure downstream traces back to a photograph that broke one of these.
Detection
Greyscale, Gaussian blur, Canny edge detection, contour extraction, largest contour by area taken as the key. Standard, and adequate — given a photograph that follows the guidelines.
Profile
The outline is reduced to a bounding box and sampled along its length. This is the step that is not finished — see below.
Mesh
Vertices generated along the sampled profile at a fixed blank thickness, faces stitched between them, exported through trimesh. The desktop path does this from a thresholded silhouette contour and produces a real extrusion of the shape in the photograph.
Delivery
FastAPI service with Keygen licence validation and file download; a browser client; a desktop build with a machine-fingerprint licence cache; and a GitHub Actions workflow that compiles executables on release.

05Outcome

What works: the desktop application loads an image, thresholds it, finds the outer contour and extrudes it into a mesh you can open in a slicer. Licence validation works end to end against the Keygen API, on both the server and the desktop, with the desktop caching a machine fingerprint so it does not need a round trip every launch. The release pipeline builds and publishes executables without manual steps.

What I actually learned from it was about scope. Four surfaces is not four times the work of one — it is roughly four different projects that happen to share a core, and each surface generated its own class of problem that had nothing to do with computer vision: licence caching offline, file lifetimes on the server, build reproducibility, and explaining to a person how to hold a phone.

06Limitations

The bitting extraction is not implemented

The bitting — the cut teeth along the blade, which is the part that makes a key a specific key rather than a key-shaped object — is not being measured from the image. In backend/key_processor.py the sampled depths are generated with np.random.uniform, under a comment that reads “Simplified: vary depth randomly for demo”.

Separately, the hosted /api/generate-stl endpoint carries a TODO: Implement actual key-to-STL conversion and currently writes a placeholder file. The desktop path does produce a genuine silhouette extrusion; the server path does not.

So the accurate claim is: the system architecture is finished and the silhouette pipeline works, while the measurement at the centre of it is still a stub. That is why this is filed as a prototype and not a showcase, and why there is no public demo link — there is nothing an anonymous visitor could usefully do with it yet.

Beyond that:

  • Detection depends heavily on photograph quality; the guidelines are a workaround for a pipeline that is not yet robust to background clutter or glare.
  • Blank dimensions are hard-coded to a single standard size, so a key that is not close to that geometry will scale incorrectly.
  • No depth information is recovered — the model is an extrusion of a silhouette, which cannot represent a key's warding profile.
  • The service requires a Keygen account and product token to run at all.

07What would finish it

One thing, done properly: measure the bitting. Detect the blade edge as a one-dimensional signal along the key's long axis, calibrate against a reference of known size placed in the frame, and validate against a set of keys whose cut depths are known. Everything else on the list is downstream of having a real measurement to deliver.
